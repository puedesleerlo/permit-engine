Architecture

How the system works, from who uses it down to the parts inside it, and then what happens step by step. How it was tested is on the Testing page.

Go to the stepsOpen the running demo

This is a C4 model: the same system at three levels of zoom, each one opening a box from the level before. It is written in Structurizr, and these diagrams are drawn from its export each time the site is built, so they follow the model.

Level 1: who it serves

An application comes in, and a decision that can be retraced comes out. Two models help with reading, and neither decides. People own the rules and settle what the rules send to them.

Level 2: what runs

Zooming into Permit Engine. One program does the work, and calls OPA to run the rules. Everything it learns or decides is kept in files and a log, and the public only ever reaches a folder of exported files.

Level 3: inside the Engine

Zooming into the Engine. Each part has one job. The Reader is the only part that asks a model to read a document, and the Case pipeline turns what was stored into a decision without calling one.

How it works, step by step

Four flows through those parts. The arrow in each diagram shows who is calling whom, and the earlier steps stay drawn, so the path builds up. Parts not reached yet stay grey.

One real case, all the way through: Valley Harriers Founders Race 5K

Each step shows what happened to case R0239 in the finished run. Its documents are synthetic, like every application here, and its answers are what the models really returned. It was chosen because it reaches every step: a police email says the escort is fine “in principle”, the risk lands in the review band, and an officer decides. or open it in the replay.

1

Read the application

Once per case, ahead of time. The answers are stored, so later stages call no model.

  1. Step 1 of 8

    Open the application

    Reader to Applications

    The Reader loads the form, the cover letter and the attachments of one case.

    In case R0239

    Valley Harriers Founders Race 5K: 1,400 runners on 11 July 2027, with 7 attachments and a cover letter.

  2. Step 2 of 8

    Basic checks

    Reader to OPA

    Is the fee paid, is the form complete, is the date allowed? A failure stops the case here, before any model is called.

    In case R0239

    All three pass: fee paid (ORD-3.1), form complete (ORD-3.2), date allowed (ORD-3.3).

  3. Step 3 of 8

    Link and extract

    Reader to Agentic LLM

    In the first pass, for each kind of proof a race can need, the LLM says found or absent, gives fields with quotes, and lists documents that fit no kind. This is the only pass that reads the cover letter.

    In case R0239

    It finds 7 of 8 kinds of proof. The police email is found, with the quote “Got your note about 2027-07-11.” No police letter is in the file. Every document fits a kind.

  4. Step 4 of 8

    Quote check

    Reader to Code checks

    Each quote must appear in the named attachment and each value inside its quote, or the field counts as absent. The form and the cover letter are never allowed as sources, so a letter cannot become evidence.

    In case R0239

    9 of 9 quoted fields are verified word for word.

  5. Step 5 of 8

    Judge

    Reader to Agentic LLM

    In the second pass, in a fresh context, the LLM gets the attachments behind verified fields and the case's typed values, never the cover letter. It gives one verdict per kind of proof: supported, unsupported or contradicted.

    In case R0239

    Ambulance agreement: supported.

    Certificate of insurance: supported.

    Police escort email: unsupported. “The police email is non-committal: escort is OK in principle but not promised until the roster is out.”

  6. Step 6 of 8

    Hazard screen

    Reader to OPA

    By rules only, traffic applies if a road closes, crowd pressure if the crowd is 300 or more, and medical always.

    In case R0239

    Crowd pressure: The crowd is 300 or more.

    Medical emergency: Always, for a race.

    Traffic conflict: The race closes a road.

  7. Step 7 of 8

    Tree questions

    Reader to Jev

    One Jev request per case, with typed values, evidence records and whole plan documents. Jev returns a probability for each question on the hazards that apply. It never sees the cover letter.

    In case R0239

    • Is the crowd plan adequate? 0.73
    • Is the venue too confined for people to spread out? 0.95
    • Is the medical plan adequate? 0.99
    • Is the traffic plan adequate? 0.09

  8. Step 8 of 8

    Store the answers

    Reader to Stored answers

    All of this becomes one reading record. From here on, the case needs no model call.

Read all 8 steps as a list
  1. Open the application. The Reader loads the form, the cover letter and the attachments of one case.
  2. Basic checks. Is the fee paid, is the form complete, is the date allowed? A failure stops the case here, before any model is called.
  3. Link and extract. In the first pass, for each kind of proof a race can need, the LLM says found or absent, gives fields with quotes, and lists documents that fit no kind. This is the only pass that reads the cover letter.
  4. Quote check. Each quote must appear in the named attachment and each value inside its quote, or the field counts as absent. The form and the cover letter are never allowed as sources, so a letter cannot become evidence.
  5. Judge. In the second pass, in a fresh context, the LLM gets the attachments behind verified fields and the case's typed values, never the cover letter. It gives one verdict per kind of proof: supported, unsupported or contradicted.
  6. Hazard screen. By rules only, traffic applies if a road closes, crowd pressure if the crowd is 300 or more, and medical always.
  7. Tree questions. One Jev request per case, with typed values, evidence records and whole plan documents. Jev returns a probability for each question on the hazards that apply. It never sees the cover letter.
  8. Store the answers. All of this becomes one reading record. From here on, the case needs no model call.
2

Decide the case

Rules and arithmetic only. No model is called, so any decision can be reproduced.

  1. Step 1 of 7

    Pick up the case

    Run builder to Case pipeline

    The Run builder hands the case to the pipeline, with the weights and thresholds of the moment.

    In case R0239

    Weights version first-guess+62. Approve under 0.185, and high risk from 0.216.

  2. Step 2 of 7

    Load the reading record

    Case pipeline to Stored answers

    The pipeline starts from the stored answers, not from a new model call.

  3. Step 3 of 7

    Compare fields with the form

    Case pipeline to Code checks

    Code compares each extracted field with the form. A mismatch, such as a letter naming another date, makes the record contradicted whatever the LLM said.

    In case R0239

    6 of 6 fields compared match the form, so nothing here is contradicted.

  4. Step 4 of 7

    Requirements and rule answers

    Case pipeline to OPA

    Rego gives each requirement a status (met, failed, missing or unclear), and answers every question the form can settle.

    In case R0239

    Event insurance: met (ORD-7.1).

    • Is the crowd over 800? Yes
    • Is the race on a hot date? Yes
    • Is the hospital more than 10 km away? Yes
    • Does the route use an arterial road? No

  5. Step 5 of 7

    Work out the risk

    Case pipeline to Tree arithmetic

    Answers send the case down up to six trees. Each hazard's likelihood times its severity, summed over the hazards that apply, gives the risk.

    In case R0239

    • Crowd pressure: 0.154 × 0.431 = 0.066
    • Medical emergency: 0.108 × 0.406 = 0.044
    • Traffic conflict: 0.248 × 0.400 = 0.099

    The risk is 0.210.

  6. Step 6 of 7

    Apply the decision table

    Case pipeline to OPA

    Rego reads the table from the top, and the first match wins: returned, proposed denial, officer or approved, with the row, the reason and the clause.

    In case R0239

    Row 6: The risk is inside the review band, so an officer decides. Reason code review_band, clause ORD-20.2.

  7. Step 7 of 7

    Log the decision

    Run builder to Event log

    Every stage is written as an event, with the hashes of everything the decision used. If the write fails, the decision does not take effect.

    In case R0239

    Events 742 to 752 in the log, under rules hash d3139ed35675.

Read all 7 steps as a list
  1. Pick up the case. The Run builder hands the case to the pipeline, with the weights and thresholds of the moment.
  2. Load the reading record. The pipeline starts from the stored answers, not from a new model call.
  3. Compare fields with the form. Code compares each extracted field with the form. A mismatch, such as a letter naming another date, makes the record contradicted whatever the LLM said.
  4. Requirements and rule answers. Rego gives each requirement a status (met, failed, missing or unclear), and answers every question the form can settle.
  5. Work out the risk. Answers send the case down up to six trees. Each hazard's likelihood times its severity, summed over the hazards that apply, gives the risk.
  6. Apply the decision table. Rego reads the table from the top, and the first match wins: returned, proposed denial, officer or approved, with the row, the reason and the clause.
  7. Log the decision. Every stage is written as an event, with the hashes of everything the decision used. If the write fails, the decision does not take effect.
3

An officer reviews, and the trees learn

Each review moves named leaf weights, and later cases use them.

  1. Step 1 of 7

    Send it to review

    Run builder to Officer desk

    Every case except a returned form goes on. A case sent to an officer gets a ruling, and any other case gets a review of what the system did.

    In case R0239

    Row 6 sent this case to an officer.

  2. Step 2 of 7

    The officer rules

    Officer desk to Officer

    The officer sees the documents, the decision, the risk and the trees to give a level for. They return a ruling, risky or not, a one-line reason and a level per tree. A real deployment would use a person. In this demo an LLM stands in, always labelled as simulated.

    In case R0239

    Ruling: deny. Risky: yes.

    “The risk is too high to approve as filed: a police escort is not confirmed, the traffic plan lacks signed diversions and a clear emergency route, and a large July race on narrow streets is 18 km from the hospital.”

    crowd likelihood: possible, crowd severity: serious, medical likelihood: possible, medical severity: serious, traffic likelihood: likely, traffic severity: serious.

  3. Step 3 of 7

    Log the ruling

    Run builder to Event log

    The ruling is logged with who made it. A permit is only issued with a logged decision or ruling as its parent.

    In case R0239

    Labelled “Simulated officer: an LLM following the expert rubric”. The ruling is to deny, so no permit is issued.

  4. Step 4 of 7

    Teach the trees

    Run builder to Learning

    Every review teaches, not only disagreements. A Bayesian network works back from the outcome and the named levels, and adds shares to the counts on the leaves this case reached, after discounting their old counts.

    In case R0239

    The largest move this review made, on crowd likelihood, where crowd over 800 is yes and crowd plan adequate is yes: possible goes from 92% to 93%, on 7.8 then 8.4 cases.

  5. Step 5 of 7

    Log the new weights

    Run builder to Event log

    The new weights version is logged. If the review disagreed with the system's estimate, it is also logged as a correction, with old and new values.

    In case R0239

    The officer's review moved leaf counts on 6 trees. Weights are now first-guess+63. The review agreed with the estimate, so no correction is logged.

  6. Step 6 of 7

    Re-choose the thresholds

    Run builder to Learning

    At a set interval of reviews, the two thresholds are chosen again, because thresholds fitted to one set of weights do not fit the next.

    In case R0239

    In this run, every 10 reviews.

  7. Step 7 of 7

    Decide the next case

    Run builder to Case pipeline

    Later cases use the new weights and thresholds, and each records the version it used.

    In case R0239

    The next case in the run records weights first-guess+63.

Read all 7 steps as a list

  2. The officer rules. The officer sees the documents, the decision, the risk and the trees to give a level for. They return a ruling, risky or not, a one-line reason and a level per tree. A real deployment would use a person. In this demo an LLM stands in, always labelled as simulated.
  3. Log the ruling. The ruling is logged with who made it. A permit is only issued with a logged decision or ruling as its parent.
  4. Teach the trees. Every review teaches, not only disagreements. A Bayesian network works back from the outcome and the named levels, and adds shares to the counts on the leaves this case reached, after discounting their old counts.
  5. Log the new weights. The new weights version is logged. If the review disagreed with the system's estimate, it is also logged as a correction, with old and new values.
  6. Re-choose the thresholds. At a set interval of reviews, the two thresholds are chosen again, because thresholds fitted to one set of weights do not fit the next.
  7. Decide the next case. Later cases use the new weights and thresholds, and each records the version it used.
4

A person releases a change

Only the policy owner makes a change official, and old versions stay as they were.

  1. Step 1 of 7

    Edit a rule file

    Policy owner to Rule files

    A change is data, not code: a tree question, a setting or a first guess. A lint command checks the rule files, and a setting outside its limits stops the run.

    In this run

    One tree change exists so far: a question about major crossings on the traffic likelihood tree. It was planted to test this path, and the Testing page explains it.

  2. Step 2 of 7

    Fit a candidate

    Policy owner to Learning

    The policy owner runs train and thresholds. Models are not called again.

  3. Step 3 of 7

    Read the stored answers

    Learning to Stored answers

    Fitting reads the answers already stored for each case, so it makes no model call.

  4. Step 4 of 7

    Write the candidate

    Learning to Weights and versions

    Candidate weights and thresholds are written beside the released ones. Nothing uses them yet.

  5. Step 5 of 7

    Read the result

    Policy owner to Weights and versions

    The policy owner reads the candidate's validation result, and either releases it or leaves it.

    In this run

    Traffic likelihood loss on validation: 0.808 without the question, 0.479 with it.

  6. Step 6 of 7

    Release

    Policy owner to Learning

    The policy owner runs release under a new version name.

  7. Step 7 of 7

    Keep every version

    Learning to Weights and versions

    Release copies the candidate to the new version, with the role and the hashes it was fitted on. Released versions never change in place, and it refuses to overwrite one.

    In this run

    Version v1, from the crossings candidate, released under the policy owner role and fitted on 180 cases.

  3. Read the stored answers. Fitting reads the answers already stored for each case, so it makes no model call.

  6. Release. The policy owner runs release under a new version name.

Around the system

People and systems around Permit Engine
PartWhat it does
ApplicantPersonSends a form, a cover letter and attachments. In this demo a script writes them.
OfficerPersonRules on cases the decision table sends to an officer. In this demo an LLM stands in.
Policy ownerPersonOwns the trees, thresholds and settings, and releases new versions.
StewardPersonOwns the evidence map: which documents count as proof of what.
VisitorPersonOpens any decision in the replay and reads how it was reached. Changes nothing.
Agentic LLMExternal systemA hosted language model. Reads documents in two fixed passes with no tools. It never decides.
JevExternal systemA TypeSafe model with fixed weights. Answers narrow questions as probabilities.

What runs, and what holds data

The containers inside Permit Engine
PartWhat it does
ApplicationsContainer: FilesThe form, cover letter and attachments of each case.
Rule filesContainer: YAML, JSON, RegoThe ordinance, evidence map, trees, Rego and settings. Changing a value needs no code change.
EngineContainer: Python, command lineThe program that reads, decides, learns and publishes. It holds no policy values.
OPAContainer: Open Policy Agent, subprocessRuns the Rego policies, with no network, time or random functions.
Stored answersContainer: JSON filesOne reading record per case, and every model call keyed by a hash of its input.
Weights and versionsContainer: JSON filesCandidate and released weights with their thresholds. Released versions never change in place.
Event logContainer: SQLiteOne file per run. Triggers reject updates and deletes. Holds the hashes of what each decision used.
Exported runContainer: JSONOne finished run as a folder of static files.
File serverContainer: Python http.serverServes that one folder from 127.0.0.1. Holds no keys and has no model client.
Browser replayContainer: React, VitePlays the finished run in each visitor's browser. No action buttons.

Inside the Engine

The components inside the Engine
PartWhat it does
ReaderComponent: PythonRuns the reading stages once per case and stores the answers.
Code checksComponent: PythonThe quote check and the field comparison. Plain code with no policy values.
Case pipelineComponent: PythonTurns a stored record, weights and thresholds into a decision. A pure function of its inputs.
Tree arithmeticComponent: PythonSends a case down each tree and gives likelihood, severity, the risk sum and the highest severity.
Run builderComponent: PythonTakes cases in order, decides each, asks for a review, teaches the trees and writes the log.
Officer deskComponent: PythonHands a case to the officer and brings back the ruling.
LearningComponent: PythonApplies a review to leaf counts, fits candidates, chooses thresholds and releases versions.
ExporterComponent: PythonWrites a finished run as JSON, and scans every file for vendor names and keys first.
ReproduceComponent: PythonReruns a logged decision with no model calls, and refuses if what it used has changed.
