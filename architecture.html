Architecture

A C4 model of what exists for the demo, written in Structurizr. These diagrams are drawn from its export each time the site is built, so they follow the model.

Open the running demo

At a glance

Everything happens ahead of time on one Mac. Cases are read, decided and ruled, and the finished run is exported as a folder of static files.

A plain file server sends that folder through a Cloudflare tunnel, and each visitor’s browser replays it. No server process runs application code, no key is on the public path, and a visitor cannot trigger a model call. This site is separate, on GitHub Pages at the address on the printed poster. The demo link works during the demo period, while the Mac is on.

One case, from application to decision

Step 1 of 14

  1. Step 1 of 14: Synthetic data generator to Applications

    Writes one synthetic application: a form, a cover letter and attachments. All of it is invented, and no document holds a label.

  2. Step 2 of 14: Reader to Rego through OPA

    Basic checks: is the fee paid, is the form complete, is the date allowed? A failure stops the case here, before any model is called.

  3. Step 3 of 14: Reader to Agentic LLM

    First pass, link and extract. For each evidence type a race can need, the LLM says found or absent, gives fields with quotes, and lists documents that fit no type. This pass does read the cover letter.

  4. Step 4 of 14: Reader to Code checks

    Quote check. Each quote must appear in the named attachment and each value inside its quote, or the field counts as absent. The form and the cover letter are never allowed as sources.

  5. Step 5 of 14: Reader to Agentic LLM

    Second pass, in a fresh context: judge. It gets the attachments behind verified fields and the case's typed values, never the cover letter, and gives one verdict per type: supported, unsupported or contradicted.

  6. Step 6 of 14: Reader to Rego through OPA

    Hazard screen, by rules only: traffic if a road closes, crowd pressure if the crowd is 300 or more, medical always.

  7. Step 7 of 14: Reader to Jev

    One Jev request: typed values, evidence records and whole plan documents. Jev returns a probability for each question on the hazards that apply. It never sees the cover letter.

  8. Step 8 of 14: Reader to Stored answers

    All of this is stored as one reading record. From here on, the case needs no model call.

  9. Step 9 of 14: Case pipeline to Stored answers

    The pipeline reads the record when the run is built.

  10. Step 10 of 14: Case pipeline to Code checks

    Field comparison. Code compares fields with the form for every evidence type. A mismatch, such as a letter naming another date, makes the record contradicted whatever the LLM said.

  11. Step 11 of 14: Case pipeline to Rego through OPA

    Rego gives each requirement a status (met, failed, missing or unclear) and answers every rule question from the form.

  12. Step 12 of 14: Case pipeline to Tree arithmetic

    Tree arithmetic. Answers send the case down six trees at most. Each hazard's likelihood times its severity, summed over the hazards that apply, gives the risk.

  13. Step 13 of 14: Case pipeline to Rego through OPA

    The decision table, first match wins: returned, proposed denial, officer or approved, with the row, the reason and the clause.

  14. Step 14 of 14: Run builder to Event log

    Every stage is written as an event, with the hashes of everything the decision used. Any logged decision can be reproduced with no model calls.

One officer review teaching the trees

Step 1 of 11

  1. Step 1 of 11: Run builder to Case pipeline

    A case is decided with the weights of the moment. The run starts from the first guess, written before training by a separate agent working in a folder that held only the ordinance, hazards and question lists.

  2. Step 2 of 11: Run builder to Simulated officer

    The case goes to review, unless its form was returned. The officer gets the documents, the decision, the risk and the trees to give a level for.

  3. Step 3 of 11: Simulated officer to Expert rubric

    It reads the expert rubric. Nothing else in the run reads this file.

  4. Step 4 of 11: Simulated officer to Agentic LLM

    One call with no tools. An LLM stands in for a person, and returns a ruling, risky or not, a one-line reason and a level for each tree. A real deployment would use a person.

  5. Step 5 of 11: Run builder to Event log

    The ruling is logged and labelled: simulated officer, an LLM following the expert rubric.

  6. Step 6 of 11: Run builder to Training and evaluation

    Every review teaches, not only disagreements. A Bayesian network works back from the outcome and the named levels, and adds shares to the counts on the leaves this case reached, after discounting their old counts.

  7. Step 7 of 11: Run builder to Event log

    The new weights version is logged. If the review disagrees with the system's estimate, it is also logged as a correction, with old and new weights and counts.

  8. Step 8 of 11: Run builder to Training and evaluation

    At a set interval of reviews, thresholds are re-chosen, and one point of the learning curve is read on cases the officer never reviewed.

  9. Step 9 of 11: Run builder to Case pipeline

    Later cases use the new weights and thresholds, and each records the version it used. These weights have no test result, and the screen says so.

  10. Step 10 of 11: Static export to Event log

    When the run is finished, the export reads it, scans every file for vendor names and keys, and writes static JSON.

  11. Step 11 of 11: Browser replay to Static file server

    Each visitor's browser loads that JSON and plays the run, with the learning plots moving as reviews arrive. Nothing is being computed for them.

The planted crossings question, added and released

Step 1 of 10

  1. Step 1 of 10: Synthetic data generator to Labels and case cards

    The truth table raises traffic likelihood when a route has 3 or more major crossings. The first traffic tree does not ask about crossings. This gap is planted on purpose.

  2. Step 2 of 10: Project owner to Training and evaluation

    The project owner runs train, then thresholds, then report.

  3. Step 3 of 10: Training and evaluation to Stored answers

    Training reads stored answers and makes no model calls.

  4. Step 4 of 10: Training and evaluation to Labels and case cards

    It reads the labels of the training split to fit the leaves, and of the validation split to compare results.

  5. Step 5 of 10: Training and evaluation to Rule files

    It reads the six trees and the crossings proposal. The proposal was authored in advance and labelled so. It adds one rule question from the form, so it needs no model call and no re-read.

  6. Step 6 of 10: Training and evaluation to Weights, reports and ledger

    It writes candidate weights with and without the question, and the validation report. A tree is flagged when its mean leaf entropy is the highest of all trees and above the flag in settings.

  7. Step 7 of 10: Project owner to Weights, reports and ledger

    As policy owner, the project owner reads the validation loss with and without the question.

  8. Step 8 of 10: Project owner to Training and evaluation

    If loss falls, the project owner runs release for the crossings candidate, under a new version.

  9. Step 9 of 10: Training and evaluation to Weights, reports and ledger

    Release copies the candidate to that version, with the role and the hashes it was fitted on. Released weights never change in place.

  10. Step 10 of 10: Training and evaluation to Weights, reports and ledger

    The sealed test runs once per dataset against a named version. The ledger is written before test labels are opened, and a second run is refused.

The parts

As the model states them. The code is private for now, so this page and the results are what a reader can check from here.

The parts inside Permit Engine
PartWhat it does
Synthetic data generatorPythonWrites case cards, applications, labels, splits and the expert rubric from one seed. Its truth table stays apart from the trees and from training.
ApplicationsFilesThe form, cover letter and attachments of each synthetic case. All of it is invented.
Labels and case cardsFilesThe hidden facts and the expert's levels, written by the author's truth table. Read by training and evaluation, never by the pipeline or the reading models.
Expert rubricMarkdownThe truth table in plain words. Only the simulated officer reads it.
Rule filesYAML, JSON, RegoOrdinance, evidence map, hazards, six trees, the first guess, the planted crossings proposal, Rego policies and settings. Changing a value needs no code change.
ReaderPythonRuns the reading stages for one case ahead of time: the agentic LLM's two fixed passes, then one Jev request. Has no tool that could decide or issue anything.
Code checksPythonThe quote check and the field comparison. Plain code that holds no policy values.
Rego through OPARego, OPABasic checks, requirement status, rule questions, the hazard screen and the decision table, run as an opa eval subprocess with no network, time or random built-ins.
Tree arithmeticPythonSends a case down each tree, part way where an answer is a probability, and gives likelihood, severity, entropy, the risk sum and the highest severity.
Stored answersFilesOne reading record per case, and every model call keyed by a hash of its input, so a run can be rebuilt with no calls.
Case pipelinePythonTurns a stored record, weights and thresholds into a decision, as a pure function of its inputs.
Training and evaluationPythonFits leaf weights, chooses thresholds, applies the Bayesian update from an officer's review, releases versions, runs the sealed test once, and scores the tone cases.
Weights, reports and ledgerFilesCandidate and released weights, the validation and final reports, the spend meter and the test ledger. Released weights never change in place.
Run builderPythonBuilds one finished run ahead of time: feeds cases in order from the first guess, asks the officer, teaches the trees and writes the log.
Simulated officerPythonAn LLM following the expert rubric, standing in for a person. Rules with a one-line reason and gives a level for each tree. No tools. Always labelled as simulated.
Event logSQLiteOne SQLite file per run, with triggers that reject updates and deletes, and the hashes of everything each decision used.
Static exportPython, JSONWrites the run as a folder of JSON, scans every file for vendor names and keys, and only then replaces the old folder.
Static file serverPython http.serverA plain file server bound to 127.0.0.1. Serves one folder, holds no keys and has no model client.
Browser replayReact, VitePlays the finished run in each visitor's browser from static files, with any case open to inspect. No action buttons.

Outside the system

People and systems outside Permit Engine
PartWhat it does
VisitorPersonOpens the architecture site, then watches a finished run replay in their own browser. Changes nothing and triggers no model call.
Project ownerPersonThe author. Runs every command, and plays the policy owner and steward roles. Each action is logged with its role.
Agentic LLMOutsideA hosted language model. Used ahead of time for two fixed reading passes with no tools, and as a separate call for the simulated officer. Visitors never reach it.
JevOutsideA TypeSafe model with fixed weights. Returns a probability for a narrow question. Used ahead of time. Visitors never reach it.
Architecture siteOutsideStatic pages on GitHub Pages at the address on the printed poster. Built from this model and the report files.
Cloudflare tunnelOutsideA named tunnel from the project owner's Mac to one public hostname. The only way in from outside.
