How documents are read and checked

Before any risk is calculated, an agentic LLM reads each application’s documents, and code checks what it read. Its answers feed the risk number, but only written rules and arithmetic issue a decision.

Two fixed passes with no tools

The agentic LLM runs two fixed passes. Each response must fit a schema, and a refusal or a bad response after one retry sends the case to an officer.

First pass: link and extract

Reads the form, the attachments and the cover letter, and the list of proof kinds a race can need. It reads the cover letter on purpose, so a pushy tone has a real chance to sway it. Code never accepts the letter as proof.

Returns, for each kind: found or absent, and if found, typed fields with a quote for each. It also returns expected spectators with a quote, and any documents that fit no kind.

Second pass: judge

Reads, in a new session with no memory of the first pass, the attachments behind verified fields and the case’s typed values. Never the cover letter, and never the form’s free text.

Returns one verdict per kind of proof it was given, on one claim: does this document establish what this kind of proof requires, for this case?

Supported

The document establishes what this kind of proof requires, for this case.

Unsupported

It does not, or there is no document. In a tree this only leans the answer towards “no”.

Contradicted

The document disagrees with the application. An officer always sees the case, by row 1 of the decision table.

Then code checks the work

Plain code, with no model involved. These two checks catch invented quotes and mismatched fields, whatever the LLM concluded.

The quote check

Each quote must appear in the named attachment, after normalising whitespace, and each value must appear inside its quote. If not, the field counts as absent, and the reason is kept with the case. The form and the cover letter are barred as sources, whatever the model says.

The field comparison

For every kind of proof, code compares extracted fields with the form, as the evidence map says. A letter naming another date makes the record contradicted, whatever verdict the LLM gave. An expired certificate fails the requirement.

The evidence map

A small file of plain data that says what counts as proof of what, so changing it needs no code change.

Kinds of proof
The controlled list, each with its typed fields and allowed documents. For example, a certificate of insurance has a named insured, venue, start date, end date and coverage.
Terms
Words that mean each kind, in the documents an applicant might send.
Requirements
This requirement can be met by this kind of proof, under this clause. The decision table checks one requirement this way: event liability insurance.
What does not count
Recorded with a reason, such as an applicant’s report of a verbal promise.

A requirement’s status

  • MetThe fields match the case, and the verdict is supported.
  • FailedA document exists and a field fails a rule, such as an expired date or a wrong venue. A denial is proposed for an officer to sign.
  • MissingNo document of this kind. An officer decides.
  • UnclearThe verdict and the fields disagree. An officer decides.

A police escort and an ambulance are questions in the trees, so they move the risk, unless a letter contradicts the form.

Traps planted in the data

The data includes these patterns so the checks have something to catch. The results are on the Testing page.

A form that only asserts insurance
The form is never an allowed source of proof.
Insurance naming the wrong venue
The field comparison fails the requirement.
A substitute kind of proof, such as a broker’s letter
It is not in the evidence map, so it is listed as unmapped and goes to an officer.
A letter naming another date
The field comparison makes the record contradicted.
Instructions hidden in an attachment
The LLM has no tool that could act on them, and code still compares the fields. Scoring what the models did with them is a next step.
