Risk and rules

The AI gathers evidence and scores risk, but written rules make the decision. When the system is not sure enough, a permit officer decides.

Basic checks come first

No AI involved

Before any AI reads the application, three plain checks run as ordinary code.

Every request starts with the same three questions:

  • Is the fee paid?
  • Are the park and the date allowed?
  • Is the crowd under 500 people?

Each answer is a plain yes or no. If the form is incomplete, it goes back to the applicant. If it fails a rule, the system proposes a denial. An officer signs it, and the letter says which rule failed.

Cheap checks go first, so easy cases stop early and the AI is called only when it is needed.

Risk is measured like a formal risk assessment

For every event, the risk step asks two questions: how likely is a problem, and how bad would it be? It answers with a decision tree, and every answer carries a confidence score.

In technical terms: scoring risk

Likelihood starts from the incident rate for this class of event, adjusted by the judged facts. Impact is a weighted sum of reversibility, crowd size, duration and sensitive location, I = Σ wk ak, with weights that move only inside bounds the policy owner sets. Likelihood and impact are combined in the city’s risk and impact table, which gives the risk level shown here (low, medium or high).

Fixed checks are written in Rego and run in Open Policy Agent. Judgment checks run as TypeSafe Jev trees: Jev asks each question three times, and its raw score is later calibrated into a probability.

The risk questions are one kind of check. The permit rules use two kinds, and both work on facts the fact check has already sorted out (see how the fact check works).

Fixed checks, written as code

Some conditions are plain facts, such as the zone, or whether the required proof was sent. They are written as code rules that cite the city ordinance (the local law that sets permit rules). Each one answers yes or no.

Judgment checks, scored with confidence

Other conditions need judgment, such as: is the police escort confirmed? These run as small decision trees in TypeSafe Jev, an AI tool that answers yes-or-no questions with a confidence score, one tree per clause of the ordinance.

How the decision is made

A written rule, not the AI, makes the call. It approves only when the system is sure enough that every condition holds.

Every condition must hold. The system works out how sure it is that every condition is met at once. Strong proof on one requirement cannot make up for a missing one: one weak condition pulls the whole score down.

How sure is sure enough depends on the cost of a mistake. The city weighs what a wrong approval costs against what a wrong denial costs. For example, if a wrong approval costs four times as much, the system must be at least 80% sure before it approves on its own. Bigger events need more certainty, and when the risk level is high an officer always decides.

People stay in charge. Only the policy owner (the person who signs off on the permit rules) changes the rules and the costs. Officers’ rulings tune how cautious the system is, inside the owner’s limits. Every change is tested on past cases first and can be undone. Read how officers’ rulings teach the system.

Red flags are set by the city. An attachment contradicts the request, the AI is unsure whether the event has insurance or safe emergency exits, or no rule fits the request. Any red flag sends the case to an officer.

In technical terms: the decision rule

Each Jev score s is calibrated into q = P(met | s), the chance the condition is really met, using a map fitted on officers’ rulings from spot checks (isotonic regression, or Platt scaling while rulings are few). Fixed Rego checks give q = 1 or 0.

Eligibility is p = Π qi over the conditions that apply. The threshold is t = cFA ÷ (cFA + cFD), where cFA is the cost of a wrong approval and cFD the cost of a wrong denial. Demo values: 0.6 for low risk, 0.8 for medium risk.

At the start q is capped at 0.9, so a case with six judged conditions reaches at most p = 0.53: officers see nearly everything until the calibration earns trust. Each decision logs p, t, every qi, the risk level and all versions used.

Pressure can’t buy a permit

A pushy letter gets the same answer as a plain one. The system measures pressure only to prove that it changes nothing.

Measured

The pressure meter scores how pushy a letter is: urgency, repetition, “I know the mayor”.

Never used to decide

The score is watched and kept on file, but it never feeds the decision. Officers never see it.

Checked for no effect

A weekly check confirms the score has no effect on outcomes. If pushy letters start winning more often, it is flagged.

The headline test writes the same request four ways: plain, persuasive, insistent and “I know the mayor”. All four should get the same decision. Results pending. See how the system is tested.

The life of a case

Every request moves through the same states. The system, an officer, the applicant or the clock moves it on, and every move is written to a shared log.

Other states

On hold, waiting for proof
The applicant is asked once, in one letter that lists all the missing proof. New proof sends the case back to assessing. If there is no reply, an officer decides.
Denied
The letter cites the failed clauses. An officer signs every denial.
Appealed
A denial can be appealed. A different officer reviews it, under the rules in force on the day it was submitted.
Withdrawn
The applicant withdrew the request.
Revoked
A permit issued by mistake is taken back by an officer.

The stop switch

The permit office can stop the automatic path at any time. Every case in assessing moves to officer review, and nothing is issued automatically until the switch is lifted.

Before any type of decision is allowed to run automatically, the stop switch must work in a drill and a wrong permit must be revocable.
